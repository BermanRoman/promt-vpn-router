# Приёмка: доказательства и границы

Приёмка подтверждает заявленный профиль на конкретных версиях, устройствах и сетях.

Локальный синтаксический тест, исправный сервер и тест из namespace имеют разные области доказательства; ни один из них не заменяет физический клиентский путь.

## Условия допуска

- Выбран single-exit или split-exit, утверждены исключения и поведение при отказе.
- Подтверждены версии, исходный baseline, резервная копия и путь управления, а для роутера — модель/ревизия и пакеты.
- При настройке роутера физический WAN прошёл отдельную проверку до VPN: выданный либо статический адрес, маршрут, пять минут устойчивости и TLS с LAN-клиента, дополнительно CHAP/IPCP для PPPoE.
- Конфигурация Xray проходит проверку фактическим целевым core, а для OpenWrt firewall проходит fw4 check на устройстве до активации.
- Негативные тесты, перезапуск, reboot и допустимая краткая потеря связи согласованы; доступ для восстановления проверен.
- При split-exit для отрицательного теста допуска подготовлена отдельная тестовая учётная запись без доступа к личному выходу.

## Матрица проверки

Проверки LAN/WAN, UCI/fw4, прошивки и перезапуска роутера применяются только при `router: true`.

Без роутера проверяются фактическая сеть и защита клиентского приложения, а разделение личного выхода и чужих допусков — только при split-exit.

Блокировка рекламы и обновление списков обязательны при `adfilter_enabled: true`, но работоспособность DNS и его выбранное поведение при отказе проверяются в любом профиле.

FakeDNS, его mapping и повторный sniffing проверяются только если эта схема используется.

| Проверка | Метод и ожидаемое доказательство |
| --- | --- |
| Адресация LAN | Новый физический клиент получает корректные DHCP-шлюз/DNS; нет конфликтов DHCP и адресов |
| Базовый WAN | Фактические MTU, адрес и маршрут, пять минут устойчивости, DNS/TLS; для PPPoE дополнительно CHAP/IPCP и PPP MTU |
| Single-exit | RU-сервис идёт напрямую; обычный внешний запрос выходит через NL; направление подтверждено наблюдением пути, а не только открытием страницы |
| Split-exit | Выбранный сервис выходит через личный регион посредством NL; обычный внешний трафик остаётся NL; RU остаётся direct |
| DNS | На роутере проверен перехват UDP/TCP53, в приложении — его фактический DNS-путь; обычные ответы соответствуют политике, при включённом фильтре реклама блокируется; нет неутверждённого fallback |
| IPv6 | Для IPv4-only: AAAA-политика и попытка реального IPv6-соединения согласованы, IPv6 не обходит IPv4 VPN; на роутере дополнительно проверены sysctl/UCI и LAN guard |
| Транспорт | Новые TCP и UDP; для нужных приложений отдельно QUIC; успешный TCP не доказывает UDP |
| Локальная сеть | Доступ к LAN и управлению сохраняется в нормальном и аварийном состояниях |
| Внешние сокеты | Из независимой сети нет открытого proxy, публичного рекурсора и административного API; учтены IPv4/IPv6 и внешний firewall |
| Личный допуск | Подписка только владельцу; рабочий inbound содержит только нужные допуски; чужая учётная запись отклоняется |
| Клиентская выдача | Проверен фактический профиль после применения, затем обновление подписки и работа реального приложения |
| TLS | Имя/SNI, доверие, срок, выдаваемая цепочка и соответствие рабочей пары; проверена цепь обновления |
| Ресурсы | RAM, overlay/диск, холодный старт, нагрузка и скорость на нужном физическом пути с указанной длительностью |

Прямой RU-маршрут подтверждать ограниченным счётчиком или захватом только нужного назначения без сохранения payload и пользовательских метаданных в переносимый отчёт.

Внешний IP подтверждает наблюдаемый выход конкретного запроса, но не всю политику приложения.

## Испытания закрытого выхода

Каждый отказ моделируется отдельно с заранее указанным способом восстановления, ограничением времени и подтверждением восстановления после теста.

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Остановка Xray на роутере | Публичный LAN TCP/UDP/ICMP не уходит прямо, включая ранее установленные потоки; LAN доступен |
| Отсутствует policy route/rule | Guard сохраняет закрытый выход независимо от наличия listener |
| Перезапуск firewall | Нет открытого окна LAN → публичный WAN; guard восстановлен и фактически действует |
| Reboot роутера | DHCP/DNS, policy routing, guard и VPN восстанавливаются в правильном порядке; до готовности нет утечки |
| Недоступен NL | Нет прямого обхода для зарубежных назначений; фактическое поведение RU соответствует выбранной архитектуре |
| Недоступен личный регион | Только для split-exit: выбранный сервис блокируется без NL/direct fallback; обычный NL и RU direct работают |
| Недоступен выбранный DNS | Нет ответа через запасной неутверждённый resolver; восстановление DNS подтверждено |
| Потеря FakeDNS mapping | Неизвестный/устаревший FakeIP блокируется; чужой Host/SNI не создаёт иной маршрут |
| ECH/конфликтующий Host | Восстановленное из metadata имя не подменяется повторным sniffing на NL |

Для общего guard из [router.md](router.md) остановка Xray закрывает также RU-трафик; это ожидаемое поведение, которое следует явно согласовать до испытания.

Отказ личного региона можно сначала воспроизвести на изолированном core с точными правилами, но такой тест не объявлять отказом проверенной рабочей ноды.

Результат действующего отказа указывать отдельно, если он был разрешён и действительно выполнен.

## Минимальный отчёт

Для каждого пункта записать статус OK / WARN / FAIL / UNKNOWN / N/A, время, метод, ожидаемое поведение, наблюдение и область проверки.

N/A допустим для компонентов, исключённых из выбранного профиля: роутера, дополнительного выхода, фильтра или FakeDNS.

Отсутствие требуемого устройства, доступа или разрешения означает UNKNOWN, а не успех.

Обязательный FAIL или UNKNOWN не позволяет объявить соответствующий компонент принятым.

Отчёт содержит только обезличенные роли узлов, версии, результаты и ссылки на локальные защищённые доказательства в окружении владельца.

Не переносить IP клиентов, реальные домены инфраструктуры, UUID, подписки, SSID, payload, ключи и персональные абсолютные пути в публичный пакет.

Указать, проверены ли реальный Wi-Fi, мобильный клиент, существующие UDP-сессии, QUIC, целевая скорость и восстановление резервной копии; непроверенное оставить ограничением.

## Известные границы

FakeDNS охватывает запросы через контролируемый DNS и доступное сопоставление, но не гарантирует распознавание собственного DoH/DoQ приложения или старого реального IP.

Общий CDN и непрозрачный протокол могут сделать принадлежность выбранному сервису неразличимой без более широкого ограничения трафика.

DNS-фильтрация не доказывает исчезновение косметической рекламы и не гарантирует работу авторизации внутри приложения.

Серверный vpn-check не доказывает клиентский маршрут; успешный тест одного устройства не переносится на все устройства автоматически.

После изменений повторять затронутые проверки и их зависимости; полный цикл требуется при изменении архитектуры, ядра/прошивки или наличии необъяснённого сбоя.
